# Task Workflow

## 1. Цель процесса

* задачи имеют единый формат;
* по идентификатору задачи понятно, к какой области она относится;
* крупные Feature разбиваются на независимые подзадачи;
* каждая задача связана с веткой и Pull Request;
* состояние разработки отражается в GitHub Project;
* завершённые задачи соответствуют единому Definition of Done.

---

## 2. Идентификатор задачи

Каждая задача получает уникальный идентификатор формата:

`[STACK-MODULE-ID]`

Где:
* **STACK** — технологический стек (`FRONTEND`, `BACKEND`, `FULLSTACK`);
* **MODULE** — доменная область проекта;
* **ID** — порядковый номер задачи внутри модуля, начиная с `01` по нарастающей (`01`, `02`, `03`...).

Для подзадач (**Sub-issues**) родительской задачи используется иерархическая сквозная нумерация:

`[STACK-MODULE-ID-1]`, `[STACK-MODULE-ID-2]`, `[STACK-MODULE-ID-3]` и т.д.

Например:
* Родительская задача / Feature: `[FULLSTACK-BLOG-01] Реализовать закрепление постов за блогом`
  * Подзадача 1: `[BACKEND-BLOG-01-1] Реализовать мутацию pinPostToBlog и проверку прав`
  * Подзадача 2: `[FRONTEND-BLOG-01-2] Добавить модалку выбора свободных постов для пина`
  * Подзадача 3: `[FRONTEND-BLOG-01-3] Отобразить закрепленные посты в шапке блога`
* Независимая задача: `[BACKEND-AUTH-02] Добавить валидацию сложности пароля на уровне DTO`

### Stack

Определяет платформенную область задачи:
* `frontend` — клиентская часть (Next.js, UI, стили, клиентский GraphQL);
* `backend` — серверная часть (NestJS, GraphQL API, Prisma, Redis, S3);
* `fullstack` — сквозные фичи, требующие одновременной реализации контракта на бэкенде и интерфейса на фронтенде.

### Module

Module определяет функциональную или техническую область задачи. Модули отражают реальную доменную структуру проекта **human-draft**:

#### Модули Backend

| Модуль | Область ответственности |
| ------ | ----------------------- |
| `AUTH` | Регистрация (`signUp`), авторизация (`signIn`), завершение сессии (`signOut`), безопасность паролей (Argon2), управление сессионными cookie |
| `SESSION` | Хранилище сессий в Redis (`connect-redis`), валидация активных сессий |
| `USER` | Профили пользователей, обновление данных, поиск участников, пагинация пользователей |

| `POST` | Публикации и статьи, JSON/Markdown контент, счетчики просмотров и лайков, закрепление постов в блог, пагинация ленты |
| `BLOG` | Блоги и авторские пространства, создание/редактирование, обложки, закрепление/открепление постов |
| `COMMENT` | Комментарии к публикациям, древовидные ответы (`replies`), оптимизация выборки через DataLoader (`CommentsLoader`) |
| `TAG` | Тегирование публикаций и блогов, нормализация имен тегов, поиск по тегам |
| `STORAGE` | Загрузка файлов в AWS S3 (`@aws-sdk/client-s3`), трансформация и сжатие изображений через Sharp, валидация форматов/размеров |
| `DATABASE` | Prisma ORM, схемы данных (`schema.prisma`), миграции, сидирование (`seed.ts`), PostgreSQL адаптер |
| `REDIS` | Клиент Redis, кэширование, сессионный слой |

#### Модули Frontend

| Модуль | Область ответственности |
| ------ | ----------------------- |
| `AUTH` | Формы входа (`SignInForm`), регистрации (`SignUpForm`), валидация (Zod), табы переключения, роуты `(auth)` |
| `USER` | Страница профиля, виджет пользователя в Header, настройки профиля, загрузка аватара/обложки с кадрированием (`react-easy-crop`) |
| `SUBSCRIPTION` | Кнопки подписки/отписки (`SubscribeButton`, `UnsubscribeButton`), фильтрация контента по подпискам |
| `POST` | Карточки статей (`PostCard`), страница поста, детальный просмотр, счетчики лайков и комментариев |
| `BLOG` | Карточки блогов (`BlogCard`), страница блога, управление постами внутри блога, обложки |
| `COMMENT` | Дерево комментариев (`CommentsList`, `CommentItem`), формы добавления/редактирования комментариев |
| `TAG` | Выбор тегов (`TagsPicker`), отображение тегов (`TagsList`), поиск и фильтрация по тегам |
| `EDITOR` | WYSIWYG/Markdown редактор на базе Milkdown (Crepe), конвертация JSON в HTML (`milkdownJsonToHtml`) |
| `FEED` | Главная лента постов и блогов, таб-фильтры, бесконечная прокрутка (`useInfiniteScroll`) |
| `SEARCH` | Поисковая строка, дебаунс-поиск по статьям, блогам и авторам (`usePostsAndBlogsSearch`) |
| `UI` | Базовые компоненты дизайн-системы (Header, Footer, Dashboard, Container, Modal, Button, FormField, Skeletons) |
| `I18N` | Мультиязычность (`next-intl`), словари `ru.json` / `en.json`, переключатель языка |
| `THEME` | Переключение темной/светлой темы (`next-themes`, CSS variables в `globals.css`) |
| `API` | Apollo Client конфигурация, кодогенерация типов (`graphql-codegen`), клиентские мутации/запросы |

#### Модули Fullstack

Используются для сквозных задач, затрагивающих клиент и сервер:
* `AUTH`, `USER`, `SUBSCRIPTION`, `POST`, `BLOG`, `COMMENT`, `TAG`, `STORAGE`, `FEED`, `SEARCH`.

## 3. Регламент и структура Эпиков (Feature)

### 3.1. Определение и назначение Эпика (Feature)

**Эпик (Feature Issue)** — это крупная функциональная или архитектурная веха проекта, которая не может быть реализована в рамках одного PR и объединяет группу взаимосвязанных подзадач (**Sub-issues**).

Родительская Feature используется для:
* описания общей бизнес-цели и пользовательской ценности;
* хранения сквозного архитектурного и продуктового контекста;
* объединения связанных изменений (Backend API + Frontend UI + Schema);
* мониторинга прогресса реализации фичи (GitHub Sub-issues progress);
* итоговой сквозной интеграции и тестирования.

> **Важно:** Непосредственная разработка в ветках ведётся строго в рамках подзадач (`Sub-issues`). В родительской Feature код не коммитится, за исключением итогового мерж-PR всей интеграционной ветки (если применялся `feature/*` бранч).

### 3.2. Формат заголовка Эпика

`[EPIC-MODULE] Название крупной фичи или функционального блока`

Примеры:
* `[EPIC-POST] Полнофункциональный редактор статей (Milkdown) и просмотр публикаций`
* `[EPIC-USER] Профиль автора, кадрирование аватара/обложки и настройки аккаунта`
* `[EPIC-FEED] Главная страница: лента публикаций, фильтры и глобальный поиск`

### 3.3. Шаблон структуры описания Эпика

```markdown
# [EPIC-MODULE] Название фичи

## 1. Цель и ценность
Какую бизнес-задачу или потребность пользователей решает фича.

## 2. Пользовательские сценарии (User Stories)
- Как [роль], я хочу [действие], чтобы [результат].

## 3. Архитектурный план
### 3.1. Backend & Data Layer
- Изменения в Prisma схеме / миграции;
- Новые/модифицированные GraphQL Queries / Mutations;
- Сервисы, кэш (Redis), S3 хранилище.

### 3.2. Frontend Layer
- Новые маршруты (App Router: `app/...`);
- Модули и виджеты (`src/modules/...`);
- Сторы (Zustand) и Apollo-хуки;
- Интернационализация (словари `ru.json`, `en.json`).

## 4. Декомпозиция на Sub-issues
- [ ] [BACKEND-MODULE] Краткое описание задачи
- [ ] [FRONTEND-MODULE] Краткое описание задачи
- [ ] [FULLSTACK-MODULE] Краткое описание задачи

## 5. Критерии приёмки Эпика (Definition of Done Feature)
- Условия, при которых фича признается полностью готовой к релизу в `dev` / `main`.
```

## 4. Заголовок Issue

Формат:

`[ID] Краткое описание результата`

Например:
* `[FULLSTACK-POST-01] Реализовать закрепление постов за блогом`
* `[BACKEND-COMMENT-02] Добавить DataLoader для выборки вложенных ответов`
* `[FRONTEND-USER-01] Добавить модальное окно кадрирования аватара`
* `[BACKEND-POST-01-1] Реализовать проверку прав автора при прикреплении статьи`

Заголовок должен описывать конкретный результат.

## 5. Описание задачи

Задача должна содержать достаточно информации, чтобы разработчик понимал ожидаемый результат без необходимости восстанавливать требования самостоятельно.

Рекомендуемая структура:

### Структура шаблона

```markdown
## Контекст
Почему требуется изменение и какую проблему оно решает.

## Требуется
Что необходимо реализовать.

## API / контракт
Если задача изменяет API:
* endpoint / GraphQL query / mutation;
* input arguments;
* response types;
* error codes;
* другие изменяемые контракты.

## Проверки и ограничения
Необходимые бизнес-правила и валидация.

## Критерии приёмки
Наблюдаемые условия, при выполнении которых задача считается реализованной.
```

### Пример заполнения

```markdown
## Контекст
Пользователи должны иметь возможность закреплять свои свободные публикации внутри созданных блогов для структурирования материалов.

## Требуется
- Реализовать мутацию `pinPostToBlog(postId: String!, blogId: String!): PostModel!`.
- Проверить, что вызывающий пользователь является автором поста и автором блога.
- Проверить, что пост ранее не был привязан к другому блогу.
- Обновить связь поста с блогом в базе через Prisma.

## API / контракт
- Mutation: `pinPostToBlog(postId: String!, blogId: String!): PostModel!`
- Ошибки: `404 Not Found` (пост или блог не найден), `403 Forbidden` (чужой пост или блог).

## Критерии приёмки
- При успешном выполнении пост отображается в списке постов блога.
- Пост исключается из списка доступных для закрепления (`getFreePostsForPin`).
- Попытка закрепить чужой пост возвращает ошибку доступа.
- Повторный вызов мутации на уже закрепленный пост возвращает валидную ошибку.
```

## 6. Система лейблов (плашек) GitHub

Каждая Issue в обязательном порядке маркируется набором лейблов.

> **Основное правило лейблов:**
> Каждая задача **должна содержать хотя бы один лейбл каждого вида** (`stack:*`, `type:*`, `feature:*`, `module:*`).
> Лейблы типа `module:*` и `feature:*` **могут повторяться**, если задача затрагивает несколько областей.

Схема обязательного набора лейблов задачи:
```text
[Task Issue]
  ├── 1x stack:*   (ровно один лейбл стека)
  ├── 1x type:*    (ровно один лейбл характера изменения)
  ├── 1+ feature:* (одна или несколько функциональных фич)
  └── 1+ module:*  (один или несколько технических модулей)
```

---

### 6.1. Плашки стека (`stack:*`) — Полный список

Определяют платформенный контекст выполнения задачи:

| Лейбл | Описание |
| ----- | -------- |
| `stack:frontend` | Клиентская часть: Next.js 16, React 19, Tailwind CSS, Zustand, Apollo Client, Milkdown |
| `stack:backend` | Серверная часть: NestJS 11, Apollo Server, GraphQL, Prisma 7, PostgreSQL, Redis, S3 |
| `stack:fullstack` | Сквозная задача: требует изменений как на бэкенде (API, БД), так и на фронтенде (UI, стор) |

---

### 6.2. Плашки типов (`type:*`) — Полный список

Определяют характер и цель выполнения задачи:

| Лейбл | Описание |
| ----- | -------- |
| `type:feature` | Разработка новой функциональности или расширение существующей |
| `type:bug` | Исправление ошибок, сбоев или некорректного поведения |
| `type:refactor` | Изменение и оптимизация структуры кода без изменения внешнего поведения |
| `type:test` | Написание или доработка тестов (Unit, Integration, E2E) |
| `type:docs` | Создание или актуализация технической документации |
| `type:chore` | Рутинные технические задачи, обновление зависимостей, правка конфигураций |

---

### 6.3. Плашки фич (`feature:*`) — Функциональные области human-draft

Определяют продуктовую/бизнес-область, к которой относится функционал:

| Лейбл | Описание функциональной области |
| ----- | -------------------------------- |
| `feature:auth` | Регистрация, авторизация, сессии, безопасность паролей, логаут |
| `feature:user` | Профиль пользователя, аватар, обложка, персональные данные, список участников |
| `feature:post` | Статьи и публикации, Markdown-контент, просмотры, лайки, публикация |
| `feature:blog` | Блоги, авторские пространства, подборки, закрепление статей |
| `feature:comment` | Комментарии к статьям, древовидные ответы (`replies`), реакции |
| `feature:tag` | Тегирование контента, каталог тегов, фильтрация по тегам |
| `feature:subscription` | Подписки и отписки на авторов, списки фолловеров |
| `feature:feed` | Главная страница, общая лента публикаций, вкладки-фильтры |
| `feature:search` | Глобальный поиск по статьям, блогам, авторам и тегам |
| `feature:settings` | Настройки аккаунта, персональные предпочтения пользователя |
| `feature:call` | Голосовые/видео звонки и WebRTC-коммуникации (резервный модуль расширения) |

---

### 6.4. Плашки модулей (`module:*`) — Технические компоненты

Определяют конкретные технические подсистемы и библиотеки, в которых происходят изменения (могут комбинироваться):

| Лейбл | Техническая зона ответственности |
| ----- | --------------------------------- |
| `module:ui` | Компоненты интерфейса, верстка, Tailwind CSS v4, адаптивность, дизайн-система |
| `module:editor` | Ядро редактора Milkdown (Crepe, ProseMirror), HTML-парсеры, рендерер контента |
| `module:api` | GraphQL резолверы, схемы, DTO инпуты, Apollo Client запросы/мутации |
| `module:db` | Схема Prisma (`schema.prisma`), миграции, сиды (`seed.ts`), PostgreSQL |
| `module:redis` | Клиент Redis, кэширование, хранилище активных пользовательских сессий |
| `module:storage` | Интеграция с AWS S3, загрузка медиа, оптимизация и сжатие изображений через Sharp |
| `module:i18n` | Интернационализация (`next-intl`), словари переводов (`ru.json`, `en.json`) |
| `module:theme` | Поддержка светлой и тёмной темы (`next-themes`, CSS-переменные в `globals.css`) |
| `module:state` | Клиентские хранилища состояния (Zustand stores) |
| `module:auth` | Механизмы авторизации: хеширование Argon2, сессионные куки, гарды `@Auth` |
| `module:repo` | Структура репозитория, конфиги сборки, TypeScript, ESLint, Prettier |
| `module:infra` | Docker, CI/CD пайплайны GitHub Actions, переменные окружения `.env` |
| `module:chore` | Обновление npm-пакетов, очистка легаси, техническое обслуживание |

### 6.5. Примеры обязательной комбинации лейблов

1. **Создание мутации прикрепления поста к блогу:**
   * `stack:backend`
   * `type:feature`
   * `feature:blog`, `feature:post`
   * `module:api`, `module:db`

2. **UI-модалка кадрирования аватара:**
   * `stack:frontend`
   * `type:feature`
   * `feature:user`
   * `module:ui`, `module:storage`, `module:state`

3. **Баг с отображением ответов на комментарии:**
   * `stack:frontend`
   * `type:bug`
   * `feature:comment`
   * `module:ui`, `module:api`

4. **Добавление CI проверки линтеров и тестов:**
   * `stack:fullstack`
   * `type:chore`
   * `feature:settings`
   * `module:infra`, `module:repo`

---

## 7. Поля GitHub Project

Для рабочих задач используются следующие статусы:

* `Backlog` — задача существует, но ещё не подготовлена к разработке.
* `Ready` — задача декомпозирована, содержит требования, готова к взятию в работу.
* `In Progress` — задача находится в активной разработке.
* `In Review` — открыт Pull Request, код проходит Code Review.
* `Testing` — реализация проходит ручную или автоматизированную проверку критериев приёмки.
* `Blocked` — выполнение невозможно продолжить из-за внешней блокирующей зависимости.
* `Done` — задача полностью завершена и соответствует Definition of Done.

---

## 8. Работа с задачей

Разработчик выбирает задачу со статусом `Ready`.

Перед началом работы:
1. Назначает себя **Assignee**;
2. Переводит задачу в `In Progress`;
3. Создаёт рабочую ветку от актуальной ветки `dev`.

Разработчик не должен одновременно держать большое количество задач в `In Progress`.

> **Основной принцип:** закончить текущую задачу прежде, чем начинать следующую (WIP-лимит).

---

## 9. Ветки

Для каждой непосредственно реализуемой задачи создаётся отдельная ветка.

### Ветки интеграции

* Разработка ведётся от `dev`.
* В `main` попадает только то, что прошло все проверки и признано готовым к релизу.
* Релиз в `main` делается отдельным PR из `dev`, когда фича доведена целиком.

### Именование веток

Название ветки **обязательно** должно содержать номер issue. Это позволяет однозначно связать ветку, PR и задачу:

| Тип задачи | Формат имени ветки | Пример |
| ---------- | ------------------ | ------ |
| Feature | `feature/<issue-number>-<short-description>` | `feature/999-photo-editor` |
| Bugfix | `bugfix/<issue-number>-<short-description>` | `bugfix/665-short-problem-description` |
| Refactoring | `refactor/<issue-number>-<short-description>` | `refactor/112-remove-old-snapshot` |
| Documentation | `docs/<issue-number>-<short-description>` | `docs/232-update-group-api` |
| Tests | `test/<issue-number>-<short-description>` | `test/442-password-validator` |

Подробное пошаговое руководство по ветвлению, `rebase`, работе с Sub-issues и разрешению конфликтов описано в [git-guide.md](git-guide.md).

## 10. Commit Messages

Для сообщений коммитов используется единый формат на основе **Conventional Commits** с обязательным указанием модуля.

### Формат

```text
<type>(<module-name>): <short description>
```

Пример:

```text
feat(post): add pin post to blog mutation
```

### Type

| Type | Когда используется |
| ---- | ------------------ |
| `feat` | новая функциональность |
| `fix` | исправление ошибки |
| `refactor` | изменение структуры кода без изменения внешнего поведения |
| `test` | добавление или изменение тестов |
| `docs` | изменение документации |
| `perf` | оптимизация производительности |
| `build` | изменения системы сборки или зависимостей |
| `ci` | изменения CI/CD |
| `chore` | технические изменения, не относящиеся к production-коду |

### Description

Описание коммита должно быть:
* коротким и конкретным;
* написанным на английском языке;
* описывать выполненное изменение;
* начинаться со строчной буквы;
* без точки в конце.

**Хорошо:**
```text
fix(comment): validate empty text input
feat(blog): add cover image upload
refactor(storage): migrate sharp resizing to separate utility
```

**Плохо:**
```text
fix
changes
fix bug
post update
feat(post): some changes
feat(auth): Fixed stuff.
```

### Несколько коммитов в рамках одной задачи

Одна задача может содержать несколько логически самостоятельных коммитов. Не требуется искусственно сжимать всю реализацию в один коммит. При этом каждый коммит должен представлять логически целостное изменение и оставлять проект в компилируемом/рабочем состоянии.

### Основное правило коммита

Commit должен отвечать на три вопроса:
1. **Какой тип изменения выполнен?**
2. **В каком модуле было изменение?**
3. **Что конкретно изменилось?**

```text
feat(blog): add cover image upload
│    │      │
│    │      └─ что изменилось
│    └──────────────── в каком модуле изменилось
└───────────────────── тип изменения
```

## 11. Pull Request

Один Pull Request должен соответствовать одной задаче или одной логически целостной подзадаче.

* В названии PR указывается ID задачи:
  `[FULLSTACK-POST-01] Реализовать закрепление постов за блогом`
  или для подзадачи:
  `[BACKEND-POST-01-1] Реализовать проверку прав автора при прикреплении статьи`
* PR обязательно связывается с соответствующей GitHub Issue (ключевыми словами `Closes #123` или через UI).
* При открытии PR задача в GitHub Project переводится: `In Progress → In Review`.

Во время Code Review проверяются:
* корректность реализации;
* архитектурное решение;
* соответствие требованиям и критериям приёмки;
* обработка ошибок и краевые случаи;
* тесты и прохождение линтеров;
* обратная совместимость контрактов;
* безопасность (auth, permissions, sanitization) и производительность (отсутствие N+1).

Замечания Code Review исправляются в той же ветке.

Правила оформления PR и классификация комментариев (`blocking:`, `question:`, `suggestion:`, `nit:`) подробно описаны в [pr-workflow.md](pr-workflow.md).

---

## 12. Rework после Code Review

* Отдельный статус `Rework` не используется.
* Если во время Review найдены замечания, задача остаётся в статусе `In Review`.
* Разработчик вносит исправления в ветку, пушит коммиты, после чего ревьюер проводит повторную проверку.
* Если выяснилось, что требуется существенная переработка требований или архитектуры, задача возвращается: `In Review → In Progress`.

---

## 13. Testing

После успешного прохождения Code Review задача переводится:

`In Review → Testing`

На этом этапе проверяется выполнение Acceptance Criteria:
* основной сценарий;
* негативные сценарии и валидация;
* корректность возвращаемых кодов ошибок;
* права доступа и авторизация;
* интеграция frontend/backend;
* изменения API и обратная совместимость;
* отсутствие регрессии в смежной функциональности.

Если найден дефект реализации текущей задачи — она возвращается в `In Progress`.
Если обнаружен отдельный независимый дефект — создаётся новая Issue с префиксом `bugfix`.

---

## 14. Blocked

Статус `Blocked` используется **только** когда разработчик объективно не может продолжить работу:
* отсутствует необходимый API другой системы/модуля;
* задача зависит от незавершённой смежной подзадачи;
* требуется архитектурное или продуктовое решение;
* недоступна внешняя инфраструктура (S3, Redis, сторонний сервис).

При переводе в `Blocked` в Issue **обязательно** указывается:
1. что блокирует работу;
2. что необходимо для разблокировки;
3. кто или какая задача является блокирующей зависимостью.

> `Blocked` запрещено использовать в значении «я пока этим не занимаюсь».

---

## 15. Definition of Done для подзадачи

Подзадача считается `Done`, если:
* реализация полностью завершена;
* все Acceptance Criteria выполнены;
* необходимые тесты написаны и успешно проходят;
* линтеры и тайпчеки проходят без ошибок;
* PR успешно прошёл Code Review;
* все замечания ревьюера исправлены;
* документация / GraphQL схема актуализированы;
* реализация прошла этап `Testing`;
* PR смержен в целевую ветку (`dev` или feature-ветку).

Только после этого статус меняется: `Testing → Done`.

---

## 16. Definition of Done для Feature

Родительская Feature считается `Done`, если:
* завершены все обязательные Sub-issues;
* интеграция подзадач проверена комплексно;
* Feature выполняет общие Acceptance Criteria;
* регрессионные проверки успешно пройдены;
* документация модуля актуализирована;
* итоговый PR фичи прошёл Code Review;
* ветка Feature смержена в `dev`.

---

## 17. Основной принцип

GitHub Project должен отражать **реальное состояние разработки**.

**Запрещено:**
* оставлять начатую задачу в `Ready`;
* переводить незавершённую задачу в `Done`;
* держать заблокированную задачу в `In Progress` без комментария;
* создавать PR без связанной Issue;
* добавлять незапланированные задачи в Sprint без согласования;
* использовать одну Issue для нескольких независимых изменений;
* использовать одну ветку для нескольких независимых задач.

Если состояние разработки изменилось — статус задачи в GitHub Project должен быть немедленно обновлён.
