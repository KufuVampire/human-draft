# HUMAN DRAFT — Pull Request и Code Review

Этот документ устанавливает единые правила оформления Pull Request (PR) и составления комментариев Code Review для проекта **human-draft**.

Основной регламент работы с задачами, ветками и статусами описан в [Task Workflow](task-workflow.md).

---

# 1. Оформление Pull Request

При создании Pull Request на GitHub автоматически подставляется шаблон из `.github/pull_request_template.md`.

* Один Pull Request строго соответствует **одной задаче** или **одной логически целостной подзадаче**.
* Формат заголовка PR:
  * Для самостоятельной задачи / Feature: `[STACK-MODULE-ID] Краткое описание результата`
  * Для подзадачи: `[STACK-MODULE-ID-N] Краткое описание результата`
  * Примеры:
    * `[FULLSTACK-POST-01] Реализовать закрепление постов за блогом`
    * `[BACKEND-POST-01-1] Реализовать мутацию pinPostToBlog и проверку прав`
    * `[FRONTEND-USER-02] Добавить модальное окно кадрирования аватара`

---

## Структура описания PR

### 1.1. Связанная задача (Related)

Содержит идентификатор задачи и ссылки на GitHub Issues:
* `Closes #123` — связывает PR с реализуемой Issue и автоматически закрывает её после мержа в `dev` или `main`.
* `Parent: #110` — указывает ссылку на родительскую Feature / Epic (если PR реализует `Sub-issue`).

```markdown
## 🔗 Связанная задача

Closes #123
Parent: #110

ID: `[BACKEND-POST-01-1]`
```

> Если родительской Issue нет, строку `Parent` следует удалить. Номер Issue нельзя оставлять пустым.

---

### 1.2. Что было сделано (What was done)

Кратко и технично описывает фактически выполненные изменения:
* помогает ревьюеру быстро понять границы diff;
* не дублирует целиком описание задачи, а фиксирует факты реализации.

Пример:
```markdown
## 📝 Что было сделано

- Добавлена GraphQL мутация `pinPostToBlog(postId, blogId)`.
- Реализована проверка владения постом и блогом через `PostService` и `BlogService`.
- Добавлена валидация исключения повторного закрепления.
- Написаны unit-тесты для сценариев успешного пина и попытки прикрепить чужой пост.
```

---

### 1.3. Технические особенности (Implementation notes)

Содержит важные технические и архитектурные решения, которые неочевидны непосредственно из diff:
* изменения схемы Prisma и миграции базы данных;
* изменения GraphQL схемы (Queries, Mutations, Input DTO);
* транзакционность Prisma (`$transaction`) и обработка ошибок;
* работа с сессиями и кэшем в Redis;
* батчинг запросов через DataLoader (`CommentsLoader`);
* специфика работы с AWS S3 и обработкой через Sharp;
* клиентские сторы Zustand и инвалидация кэша Apollo Client;
* интеграция с редактором Milkdown / ProseMirror.

Для тривиальных задач раздел может быть пустым или удалён.

Пример:
```markdown
## 💡 Технические особенности (Implementation notes)

Проверка прав и связывание поста с блогом объединены в `$transaction`.
При успешном пине вызывается инвалидация кэша Apollo `getFreePostsForPin`,
чтобы свободные посты сразу исчезали из списка выбора в UI.
```

---

### 1.4. Как проверить (How to test)

Пошаговая инструкция для проверки функциональности ревьюером или автором:
* основной сценарий (happy path);
* негативные сценарии (ошибки валидации, права доступа, 404, 403);
* ожидаемый результат на каждом шаге.

Пример:
```markdown
## 🧪 Как проверить (How to test)

1. Авторизоваться пользователем `user1`.
2. Создать тестовый блог и тестовый пост.
3. Выполнить мутацию `pinPostToBlog(postId: "...", blogId: "...")`.
4. Убедиться, что пост вернулся с заполненным полем `blog`.
5. Повторить вызов мутации с теми же ID — ожидать ошибку `400 Bad Request`.
6. Вызвать мутацию от лица `user2` с ID поста `user1` — ожидать `403 Forbidden`.
```

---

### 1.5. Чеклист Definition of Done (DoD)

Обязательный список проверок перед переводом PR в статус готового к мержу:
* [ ] Критерии приёмки из Issue выполнены;
* [ ] Линтер проходит без ошибок (`npm run lint`);
* [ ] TypeScript компилируется без ошибок (`tsc --noEmit`);
* [ ] Тесты написаны и проходят успешно (`npm run test`);
* [ ] Схема GraphQL и сгенерированные типы актуализированы (`npm run gql` / `db:gen`);
* [ ] Отсутствуют отладочные логи (`console.log`) и закомментированный код.

---

### 1.6. Скриншоты / Демо (Screenshots / Demo)

Обязательно для любых UI-изменений во фронтенде:
* скриншоты светлой и тёмной темы;
* gif / видео анимаций модальных окон, дропдаунов, работы редактора.

# 2. Классификация комментариев Code Review

Каждый комментарий ревьюера **обязательно начинается с префикса**, определяющего критичность и обязательность замечания:

```text
<prefix>: <техническое описание проблемы и последствий>
```

---

## `blocking:`

**Критическое замечание, блокирующее merge.** PR не может быть влит, пока проблема не устранена или не найдено альтернативное согласованное решение.

Используется для:
* багов в логике и нарушений критериев приёмки;
* проблем безопасности (отсутствие `@Auth()`, авторизации владельца ресурса);
* проблем с транзакциями, race conditions и целостностью данных в БД;
* проблемы N+1 запросов к базе (отсутствие DataLoader в GraphQL);
* падений сборки, ошибок TypeScript, сбоев тестов;
* утечек памяти, зависаний или неэффективных ререндеров React.

Пример:
```text
blocking: отсутствует проверка авторства блога. Любой авторизованный пользователь
может прикрепить свой пост к чужому блогу. Необходимо добавить проверку
blog.authorId === authorId.
```

---

## `question:`

**Вопрос или запрос пояснения.** Сам по себе не блокирует merge, но требует ответа автора для понимания контекста решения.

Используется для:
* выяснения неочевидной архитектурной логики;
* уточнения edge-cases, не отраженных в коде;
* проверки намеренности изменения контракта.

Пример:
```text
question: почему здесь используется прямой fetch вместо сгенерированного Apollo-хука useGetPostByIdQuery?
```

---

## `suggestion:`

**Рекомендация по улучшению.** Не блокирует merge, но предлагает более чистое, идиоматичное или производительное решение.

Используется для:
* декомпозиции тяжелых компонентов или методов;
* выноса дублирующейся логики в утилиты или кастомные хуки;
* улучшения типизации (замена `any` на строгий union);
* оптимизации стилей Tailwind или читаемости разметки.

Пример:
```text
suggestion: эту проверку формата файла можно вынести в pipes/fileValidation.pipe.ts,
чтобы не дублировать логику валидации внутри резолвера.
```

---

## `nit:`

**Незначительное замечание (придирка).** Не блокирует merge. Автор может исправить по желанию или оставить как есть.

Используется для:
* опечаток в комментариях, строках документации или именах переменных;
* минорных улучшений нейминга;
* форматирования или импортов, если линтер их пропустил.

Пример:
```text
nit: переименуй переменную `p` в `post`, чтобы код лучше читался без контекста.
```

# 3. Требования к формулировке Review Comments

Review comment должен отвечать на три вопроса:
1. **Где** находится проблема?
2. **В чём** заключается проблема?
3. **Почему** она имеет значение (каковы технические риски)?

---

### Антипаттерны (запрещено):

```text
❌ переделай
❌ неправильно
❌ исправь
❌ зачем это?
❌ тут можно лучше
```

---

### Правильные примеры:

#### Пример 1 (Backend / Prisma & DataLoader):
```text
blocking: в резолвере CommentResolver поле replies запрашивается через прямой вызов
prisma.comment.findMany для каждого комментария. В списке из 50 комментариев это вызовет
проблему N+1. Необходимо использовать CommentsLoader.batchReplies.load(comment.id).
```

#### Пример 2 (Frontend / React & Zustand):
```text
suggestion: селектор useProfile() вызывается целиком без указания конкретного поля стора:
`const profile = useProfile()`. Это вызовет ререндер компонента при изменении любых других
полей стора. Рекомендуется использовать точечный селектор: `const profile = useProfile((s) => s.profile)`.
```

#### Пример 3 (GraphQL / Security):
```text
blocking: мутация deletePost не проверяет, принадлежит ли пост пользователю из @Authorized('id').
Пользователь может передать чужой postId и удалить чужую публикацию.
```

---

# 4. Процесс доработки и согласования (Review Loop)

1. **Ответы на замечания:** Автор PR обязан ответить на все вопросы (`question:`) и отчитаться об исправлении всех блокирующих замечаний (`blocking:`).
2. **Исправления:** Правки вносятся в ту же ветку отдельными коммитами по Conventional Commits (`fix(post): ...`).
3. **Разрешение тредов (Resolve Conversation):** Тред с замечанием закрывает **тот, кто оставил замечание**, убедившись в корректности правки (или автор, если получено подтверждение).
4. **Критерий Merge:** PR может быть смержен только тогда, когда:
   * Все `blocking:` устранены;
   * Все `question:` закрыты ответами;
   * CI проверки (GitHub Actions `ci.yml`) успешно пройдены;
   * Ветка актуализирована относительно `dev`.
